# Бесплатный открытый проект: Telegram и добровольная поддержка

> Архив решения от 18.10.2026. Владелец изменил модель 19.10.2026:
> Яндекс исключён, базовые функции работают без входа, Telegram открывает
> расширение. Актуальная реализация: [версия 0.7](community-release-0.7.md).

Дата проверки: 18.10.2026. Название Cloud Hub пока рабочее.

## Решение владельца и фактический статус

Цель: открытый код, бесплатные функции, общая аудитория в Telegram, добровольные
донаты. Для официальной сборки владелец предпочёл постоянное условие подписки
на канал. Оплата не должна определять доступ к функциям.

Подготовлен изолированный прототип сервера и библиотеки клиента. Он проверяется
локально с имитацией Telegram; живой канал, бот, Яндекс OAuth-приложение и VPS
не созданы. Клиентская библиотека ещё не подключена к окнам и запуску модулей.
Установленная версия 0.6.0 не заменена, публичный репозиторий не изменён.
По умолчанию эксперимент и блокировка выключены. Это не готовый публичный релиз.

## Юридическая проверка: результат не равен разрешению

Часть 10 статьи 8 149-ФЗ устанавливает требования к авторизации российских
пользователей российским владельцем ресурса. В тексте названы и программы для
ЭВМ. Среди предусмотренных способов есть номер оператора связи, ЕСИА, ЕБС и
информационная система с владельцем, соответствующим указанным в норме
российским критериям. Исключения только из-за бесплатности или открытого кода
в этой норме не обнаружено.

Вывод для проекта: подтвердить допустимость Telegram как единственного
механизма доступа по найденным источникам не удалось. Подписанное разрешение
с нашего сервера и переименование входа в «активацию» сами по себе этот вопрос
не решают. Это исследование текста нормы, а не юридическое заключение о нашем
конкретном продукте.

Технический прототип поэтому использует уже существующую первую авторизацию
аккаунта через Яндекс ID; Telegram — дополнительный проверяемый фактор. Это
кандидат на оценку, не утверждение, что добавление Яндекса автоматически делает
обязательную привязку Telegram допустимой.

Статья 13.55 КоАП предусматривает ответственность за неисполнение обязанности
проводить авторизацию предусмотренным способом. Выбирать классификацию
владельца и применимость санкции без оценки обстоятельств не следует.

Источники, проверенные 18.10.2026:

- [149-ФЗ, статья 8, часть 10](https://www.consultant.ru/document/cons_doc_LAW_61798/78b773a28f3ad19eb234697b20ab1d48c09f748a/).
- [КоАП, статья 13.55](https://www.consultant.ru/document/cons_doc_LAW_34661/eecaf3bcdcd8f21011f025127298179a3bfd8877/).

Вопросы для юриста перед включением обязательного доступа:

1. Применима ли ч. 10 ст. 8 к нашей локальной утилите, если доступ к её функциям
   зависит от серверного разрешения и членства в Telegram-канале?
2. Допустим ли независимый вход через Яндекс ID с дополнительной обязательной
   проверкой членства? Какие условия или изменения действительно нужны?
3. Какие основания обработки, политика, уведомления РКН, локализация и сроки
   удаления нужны для Telegram ID, аккаунта и UUID установки? Какие передачи
   возникают при запросах к Telegram и как их оформить?
4. Как оформить добровольную финансовую поддержку конкретно для владельца со
   статусом самозанятого? Не считать поступления необлагаемым подарком только
   из-за названия «донат». Нужны отдельные условия выбранного сервиса и учёт.

До решения этих вопросов production-эксперимент выключен. Разработка прототипа
продолжается; юридическое подтверждение в коде не подменяется настройкой true.

## Один сервер, две роли

Бот — интерфейс в Telegram. Наш процесс обрабатывает его события. API — точка,
к которой обращается Windows-приложение. Они используют одну базу и могут
работать на одном VPS. Не нужно арендовать сервер для каждого приложения.

В прототипе переиспользован Django и существующая авторизация. Для production
текущая конфигурация требует PostgreSQL; SQLite служит локальной разработке.
Обещание конкретного размера VPS возможно только после измерения потребления
этого состава. Биллинг и автосписания остаются выключенными.

Для первого выпуска реализован только product=cloud-hub. Перед вторым продуктом
добавим реестр разрешённых product_id, отдельные ключи/области подписей и
разрешённые клиентские конфигурации. Один бренд и канал не требуют общего
доступа приложений к локальным файлам друг друга.

## Протокол прототипа

1. Пользователь входит в первый аккаунт через подготовленный OAuth/PKCE поток.
2. Его авторизованный клиент создаёт запрос привязки сроком на 10 минут.
   В базе хранится контрольная сумма случайного токена, а не сам токен.
3. Telegram deep link открывает бота. Пользователь подписывается и нажимает
   «Проверить подписку». Bot API сообщает фактический Telegram ID.
4. Клиент получает кандидата и явно подтверждает привязку. Просто открытая
   ссылка не связывает аккаунт молча. Один Telegram ID не привязывается к двум
   разным аккаунтам. Автоматическое объединение по почте отсутствует.
5. Сервер выдаёт подписанный Ed25519 документ для UUID установки и канала.
   Для него используется собственная область подписи community/v1: старое
   платёжное разрешение нельзя использовать вместо него.
6. Изменение статуса подписки приходит на webhook. Секрет заголовка проверяется
   до обработки. Событие о вступлении само по себе не выдаёт доступ: нужна
   сверка getChatMember.
7. На выдаче разрешения сервер сверяет членство не реже чем раз в 6 часов.
   Это восстанавливает состояние после пропущенных событий. Будущий интерфейс
   должен запускать обновление в рабочем потоке и после возобновления Windows.

Выбранные интервалы:

| Состояние | Политика |
| --- | --- |
| Подписка подтверждена | Все доступные функции, без платных лимитов |
| Нет интернета / Telegram не отвечает | Сохранённое разрешение до 72 часов от подтверждения |
| Подтверждена отписка | 24 часа после первого обнаружения, затем приостановка |
| Подписка никогда не подтверждалась | Льготный доступ не выдаётся |
| Подписался снова | Каноническая проверка восстанавливает доступ |

Повтор события отписки не передвигает срок. Ответы из старого кэша не продлевают
72-часовой срок. Запоздалое событие не заменяет более новую проверку. Подписанное
решение об отсутствии доступа сохраняется; старое положительное решение с
меньшей ревизией не принимается поверх него. Ошибка HTTP не равна отписке.

Эта политика ограничивает официальную сборку, не защищает от изменения открытого
исходного кода или отката файлов человеком с полным доступом к компьютеру.

Telegram требует административного статуса бота для гарантированной проверки
других участников. Нужно явно включить chat_member в allowed_updates.
Неполученные события хранятся Telegram не дольше суток, поэтому только webhook
не обеспечивает постоянную корректность.

Источники протокола:

- [События и сроки хранения](https://core.telegram.org/bots/api#getting-updates).
- [getChatMember](https://core.telegram.org/bots/api#getchatmember).
- [Webhook и секрет заголовка](https://core.telegram.org/bots/api#setwebhook).
- [Ссылки запуска бота](https://core.telegram.org/bots/features#deep-linking).

## Данные и эксплуатация

На сервере: внутренний аккаунт, Telegram ID, UUID устройства, статус и время
проверок, короткоживущие привязки. Не нужны телефон из Telegram, список чатов,
тексты заметок, названия файлов, содержимое групп, звук или изображение камеры.
Имя пользователя @username не служит идентификатором.

Предусмотрено явное отключение Telegram с удалением его привязки, статусов и
запросов привязки. Заметки и ярлыки не удаляются. На других отключённых от сети
компьютерах старое разрешение может жить до своего срока — мгновенный отзыв
офлайн-разрешения невозможен.

До запуска ещё нужны очистка истёкших запросов по расписанию, утверждённые сроки
хранения журналов и резервных копий, ограничение частоты запросов, мониторинг,
восстановление из бэкапа и сценарии потери аккаунта. Nginx-шаблон имеет отдельную
очередь ограничения частоты для webhook. Токен бота и закрытый ключ существуют
только на сервере; клиент получает публичный ключ.

## Roadmap с критериями завершения

| Этап | Работа | Проверяемый результат |
| --- | --- | --- |
| 0. Решения | Юридическая схема доступа, обработка данных, лицензии и права | Письменное решение для точной схемы; чистый состав публикации |
| 1. Техническая база — начата | Привязка, webhook, сверка, подписи, офлайн-политика | Протокол проходит локальные тесты; production выключен |
| 2. Подключение интерфейса | Минималистичная карточка сообщества, статус, повторная проверка, отключение | Нет сетевого ожидания в UI; состояние понятно без терминов лицензирования |
| 3. Живая проверка | Реальный бот-администратор, канал, Яндекс, HTTPS, PostgreSQL, резервные копии | Два ПК, отписка/вступление, сбой провайдера, сон Windows и восстановление проверены |
| 4. Стабильный продукт | Остров, группы, поиск, таймер, автозапуск, обновление | Регрессионные сценарии и измерения CPU/RAM/энергии на ноутбуке |
| 5. Единый визуальный язык | Модули как основной экран, контекстная карточка острова, общая типографика | Единая компоновка, клавиатура, масштаб 100/125/150%, отключаемая анимация |
| 6. Открытый выпуск | GPL-совместимая публикация после проверки, инструкции сборки, релизы | Внешний участник собирает приложение из тега; нет секретов в истории |
| 7. Аудитория и поддержка | Деморолики, канал, обратная связь, необязательные донаты | Измеряем установки и возвращения, а не только подписчиков |
| 8. Следующий продукт | Выбираем по запросам пользователей | Есть самостоятельный сценарий и ресурс на поддержку двух продуктов |

Выборы интерфейса, переданные владельцем: главный экран «Модули» и
«Контекстная карточка» острова. Это направление, не обещание уже выполненного
редизайна. В интерфейс не добавляем надписи Pro и лишние рекламные блоки.

Возможные расширения: история буфера обмена с исключением секретов, быстрые
снимки экрана с аннотациями, рабочие наборы окон, спокойные локальные виджеты.
Сначала оцениваем пользу и нагрузку каждого модуля. Семь отдельных приложений
одновременно не планируем.

## Финансовая модель

Функции бесплатны. Telegram — общий канал обновлений, демонстраций, готовых
оформлений и обратной связи. Донат не влияет на права доступа. Сервис приёма
поддержки выбирается отдельно после проверки условий для владельца.

Регулярная поддержка может быть добровольной, с прозрачной отменой и без доступа
к обязательным функциям в качестве вознаграждения. Не обещаем финансировать
инфраструктуру только числом подписчиков: нужны активные пользователи, полезные
выпуски, понятные цели расходов и публичные отчёты. Платёжные реквизиты и сбор
денег в рамках этой разработки не подключались.

## Локальные проверки

Из корня checkout, с уже подготовленными окружениями:

```powershell
& '..\commercial-venv\Scripts\python.exe' -m unittest discover -s tests
& '..\account-server-venv\Scripts\python.exe' server/manage.py test accounts community
& '..\account-server-venv\Scripts\python.exe' server/manage.py makemigrations --check --dry-run
```

Внешний Telegram заменён управляемым тестовым ответом. Локальные тесты не
подтверждают доступность сервисов в РФ, production-нагрузку или правомерность.
Для PostgreSQL остаются обязательными отдельные проверки конкурентных операций.
