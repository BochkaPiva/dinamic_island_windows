## Архитектура

Windows/PySide6 → наш Django API → PostgreSQL на российском сервере.
Браузер используется для Яндекс ID и страницы ЮKassa. Отдельный большой сайт
не нужен: достаточно домена, страницы продукта/документов и нашего API.
Подписка принадлежит внутреннему UUID аккаунта. Яндекс ID определяется парой
provider/subject; совпадение почты не объединяет аккаунты. Пароль приложения
не создаётся. Повторный вход с тем же Яндекс ID восстанавливает тот же аккаунт.

На сервер попадают идентификатор провайдера, контактная почта, данные платежей,
название устройства и случайный UUID установки. Заметки, пути к файлам,
содержимое групп, изображение камеры и аудиопоток туда не отправляются.
База, резервные копии и журналы аккаунтов планируются в РФ. Отдельно нужно
утвердить политику хранения и документы оператора персональных данных.

## Вход

1. Десктоп открывает системный браузер, предварительно заняв случайный порт
   на 127.0.0.1. Генерирует state и PKCE S256.
2. Наш `/o/authorize/` отправляет пользователя на страницу входа, затем в Яндекс.
   Authlib проверяет состояние провайдерского потока; обмен кода происходит
   на сервере. Секрет Яндекса не попадает в EXE.
3. После входа наш сервер возвращает короткий код на loopback. Десктоп проверяет
   state и обменивает код с verifier на свои токены.
4. Access token живёт 10 минут. Refresh token ротируется; повтор старого токена
   отзывает семейство сеанса. В базе хранятся контрольные суммы токенов, на
   компьютере — данные, защищённые Windows DPAPI. Запросы сериализованы,
   чтобы два фоновых процесса обновления не использовали один refresh token.

Используются django-oauth-toolkit и Authlib. Не реализован собственный протокол
авторизации. Публичная регистрация OAuth-клиентов и password/implicit grants
не предоставляются. Разрешён только зарегистрированный loopback redirect
первичного клиента; динамический порт предусмотрен стандартом нативных приложений.

Google не включён в российскую конфигурацию. Способы входа для РФ требуют
проверки по ч.10 ст.8 149-ФЗ; Gmail как контактная почта — отдельный вопрос.
VK ID можно добавить отдельным адаптером после проверки условий. Связывание
провайдеров, смена контактной почты и восстановление при потере Яндекс ID
пока требуют отдельной реализации и процедуры подтверждения владельца.

## API v1

Все изменяющие операции — POST. JSON API принимает только bearer в заголовке,
не браузерную cookie и не токен в URL. HTML-начало входа защищено CSRF.

| Путь | Назначение |
|---|---|
| GET `/api/v1/config` | Только доступные способы входа и готовность оплаты |
| GET `/api/v1/account` | Тариф, срок, устройства, до 30 платежей, разрешённые планы |
| POST `/api/v1/devices` | Регистрация установки; имя и installation_id; по умолчанию 3 активных устройства |
| POST `/api/v1/devices/{uuid}/revoke` | Отключить своё устройство и отозвать его семейство токенов |
| POST `/api/v1/license` | Разрешение Ed25519 для текущей зарегистрированной установки либо null |
| POST `/api/v1/checkout` | plan, expected_amount_kopecks, expected_months, auto_renew, consent_version |
| POST `/api/v1/subscription/cancel` | Отключить следующие продления, сохранить оплаченный период |
| POST `/api/v1/logout` | Отозвать текущий сеанс; клиент удаляет локальные токены и лицензию |
| POST `/hooks/yookassa` | Уведомления; подтверждение объекта через авторизованный GET к ЮKassa |

Цену и длительность определяет сервер. Ожидаемая цена клиента служит только
проверкой, что тариф не изменился с момента показа пользователю.
Страницы browser `/auth/...` не являются самостоятельным личным кабинетом:
кабинет — нативная вкладка приложения.

## Платежи и права

Платёж сохраняется до обращения к провайдеру. UUID записи — ключ идемпотентности.
Повтор нажатия оплаты возвращает открытую операцию того же аккаунта; второй
конфликтующий платёж не создаётся. Размер, RUB, test/live, магазин и наш metadata
проверяются по каноническому ответу API. Переход return_url ничего не активирует.

Подтверждённый платёж создаёт ровно один период доступа в транзакции с блокировкой
аккаунта. Дубли и устаревшие события не продлевают срок повторно. Календарный месяц
сохраняет день-якорь: 31 января → 28 февраля → 31 марта. Изменение каталога цен
не повышает цену действующего автопродления. Разовая покупка отключает прежнее
автопродление, чтобы не менять его условия молча.

Автопродление требует отдельного согласия; сохраняются версия текста, время,
цена/период и идентификатор сохранённого способа оплаты. Номер карты/CVV не хранятся.
Доступ после отмены действует до конца оплаченного периода. Уже переданный
провайдеру платёж считается начатым: отмена предотвращает следующие списания,
но не обещает остановить операцию, уже принятую банком. Это нужно отразить в условиях.
Неуспешное продление отключает дальнейшие автоматические попытки; повторная
покупка происходит по действию пользователя.

`billing_tick` обрабатывает очередь и сверяет известные незавершённые платежи.
Если ответа не было и ID провайдера неизвестен, повторяется тот же запрос с тем
же ключом. Через 23 часа неоднозначная операция переводится в manual_review:
гарантия идемпотентности ЮKassa составляет 24 часа, повтор после неё может списать
деньги ещё раз. Новые платежи блокируются до разрешения неоднозначной операции.
Нужна операторская сверка в кабинете провайдера; автоматический поиск такой
операции по списку платежей пока не реализован.

Возврат проверяется GET по API. Полный возврат отзывает соответствующий период
и продление; частичный учитывается в журнале без автоматического отзыва всего
доступа. Возвращённый период не перекрывается будущим периодом до его начала.
`reconcile_refunds` восстанавливает пропущенные уведомления из списка возвратов.
Для пилота это ограниченный полный обход; если страниц больше лимита,
команда завершится ошибкой. Перед большим запуском нужен инкрементальный журнал
с контрольными точками и сверкой финансовых реестров.

Лицензия подписывается отдельным серверным Ed25519 ключом с purpose
`cloud-hub/license/v1`. В EXE только доверенные публичные ключи. Разрешение
ограничено установкой, оплаченным периодом и 7 днями офлайн. Клиент обновляет
его в фоне раз в 6 часов; временный сетевой сбой не удаляет действующий файл.
Подтверждённое сервером отсутствие подписки удаляет старое локальное разрешение.
Отключённое удалённо офлайн-устройство может сохранять выданный доступ до конца
разрешения: мгновенный отзыв без связи невозможен. Истечение сохраняет пользовательские
данные. Политику перевода часов, восстановления после сна, ротации ключей,
повторов с задержкой и смены аккаунта нужно дополнительно проверить до продаж.

## Чеки НПД

ЮKassa по действующей документации не автоматизирует чеки «Мой налог» для НПД.
54-ФЗ receipt в запросе не подменяет чек самозанятого. Для каждого платежа и
возврата создаётся ReceiptTask со статусом needs_operator. Сбой выдачи чека
не отбирает оплаченный доступ. Команды:

```
python manage.py receipts
python manage.py receipts --complete PAYMENT_TASK_KEY --reference REAL_RECEIPT_REFERENCE
```

Вторая команда только фиксирует УЖЕ оформленный и отправленный чек/исправление.
Она не обращается к «Мой налог». Перед продажами нужен утверждённый процесс:
ручной ограниченный пилот с контролем сроков либо проверенный официальный
партнёр для автоматизации НПД. Неофициальный API ФНС и передача пароля налогоплательщика
в наше приложение не используются. Полноценный автоматический запуск пока не готов.

## Локальная проверка

Создать отдельный venv и установить `server/requirements.txt`.
Из корня репозитория:

```
python server/manage.py migrate
python server/manage.py bootstrap_desktop
python server/manage.py test accounts --verbosity 2
python server/manage.py runserver 127.0.0.1:8000 --noreload
```

Без переменных используется локальная SQLite, DEBUG выключен, внешних учётных
данных нет. Вход честно показывает, что провайдер не подключён. Тесты используют
контролируемые ответы транспорта провайдера; настоящий вход/банк они не заменяют.
Две проверки гонок пропускаются на SQLite. Для них настроен отдельный private-only
workflow с PostgreSQL 17; он ещё не был запущен в GitHub.

## Подключение сервера

1. Выбрать домен и небольшой сервер в РФ. Приложение и БД для пилота могут быть
   на одном VPS; резервная копия должна быть вне этого VPS, тоже в РФ. Это схема
   пилота без высокой доступности. Размер и стоимость утверждаются перед покупкой.
2. Установить Linux, PostgreSQL, Python 3.14 и nginx. Создать отдельного
   непривилегированного пользователя cloud-accounts и ограниченную роль БД.
   Для production установить `requirements-production.txt` в отдельный venv.
3. Разместить исходники в /opt/cloud-accounts/server. Скопировать значения
   .env.example в EnvironmentFile /etc/cloud-accounts/environment, права 0600,
   не публиковать этот файл. Файл автоматически через dotenv не читается.
4. Создать Ed25519 ключ вне репозитория; серверный пользователь имеет только
   чтение ключа. Публичный ключ с выбранным key_id добавить в доверенный список
   десктоп-сборки; независимый ключ обновлений не переиспользовать.
5. Зарегистрировать приложение Яндекс ID: серверный callback
   `https://ВАШ-ДОМЕН/auth/yandex/callback/`, минимальные login:info и login:email.
   Секрет вне исходников. Проверить живой вход и отказ/ошибки провайдера.
6. Открыть кабинет ЮKassa для самозанятого, пройти проверку продавца и условий
   рекуррентных платежей. Сначала тестовый магазин и тестовый ключ.
   Уведомления payment.succeeded, payment.canceled, payment.waiting_for_capture,
   refund.succeeded → `https://ВАШ-ДОМЕН/hooks/yookassa`.
7. Выполнить migrate/bootstrap_desktop, collectstatic, настроить TLS и использовать
   примеры deploy/*.service, *.timer, nginx.conf.example. Заменить домен везде.
   Приложение слушает только 127.0.0.1, наружу только HTTPS через nginx; входящие
   proxy-заголовки перезаписываются, IP-список ЮKassa перепроверяется по документации.
   Не включать общий журнал с query string: в callback передаются временные коды.
8. Запускать billing_tick раз в минуту; reconcile_refunds минимум раз в час
   отдельным заданием планировщика с уведомлением об ошибке. Раз в сутки проверять
   реестры провайдера, просроченные платежи и очередь чеков. Нужны уведомления
   оператору о сбоях, просрочке сверки, TLS и резервного копирования.
9. Ежедневный pg_dump custom-format шифровать отдельным ключом и отправлять
   вне VPS. До продаж восстановить его на отдельной БД и проверить логин,
   платежи и лицензии. Зафиксировать RPO/RTO. Ключи подписи, настройки и доказательства
   согласий резервировать отдельно; восстановление не должно терять владельцев покупок.
10. Проверить production settings, реальные sandbox-сценарии и удалить тестовые
    данные до перехода на live-магазин. Не смешивать test и live в одной базе.
    Утвердить тарифы, оферту, согласие на рекуррентные списания, политику ПД,
    сроки хранения, процедуру возврата/восстановления/удаления аккаунта и чеки НПД.
    Google/международный вход согласовать отдельно, не добавлять по умолчанию.

SALES_ENABLED/RENEWALS_ENABLED оставляются 0. В production включение продаж
требует ключей и файла LAUNCH_APPROVALS_PATH со всеми существующими разрешениями
на коммерческий релиз. Сейчас все разрешения false, включая права на код,
проверку платёжного цикла, документы продавца и подпись установщика.
Это не декларация готовности продукта к продажам.

## Что ещё обязательно до запуска

- Настоящий Яндекс ID, YooKassa sandbox, затем разрешённая контрольная live-оплата.
- PostgreSQL concurrency-тесты и восстановление резервной копии на отдельной машине.
- Утверждённые тарифы: в базе пока нет продаваемых планов. add_plan создаёт
  только выключенный план; изменение цены требует нового кода тарифа.
- Восстановление аккаунта при утрате провайдера, запрос удаления ПД с сохранением
  обязательных финансовых записей, процедура поддержки и доступ оператора с MFA.
- Операторский интерфейс сверки неоднозначных платежей и чеков; сейчас есть CLI,
  а не полноценная административная панель. Нет автоматической отправки налоговых чеков.
- Наблюдаемость/уведомления, нагрузочные проверки, обновление зависимостей,
  проверка перевода времени и сна, полная проверка коммерческого обновления EXE.
- Права на код, Qt/LGPL-доставка исходников зависимостей, подписанный установщик,
  отдельный коммерческий канал и приватный репозиторий. Старый публичный GPL-репозиторий
  автоматически в закрытый не превращается.
